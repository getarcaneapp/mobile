# AGENTS.md

Arcane Mobile, React Native edition. A port of the SwiftUI app at `../ios` (the **reference app**) to Expo so it also ships on Android.

## Golden rules

1. **iOS must look and behave exactly like the reference app.** Before building or changing a screen, read the matching Swift file in `../ios/Arcane Mobile/` and port it faithfully: same layout, copy, SF Symbols, colors, spacing, ordering, empty/loading/error states, toasts, confirmations, and edge-case logic. Do not "improve" or simplify.
2. **Android gets the same features and flows**, rendered in Material 3 (Jetpack Compose via `@expo/ui/jetpack-compose`, or plain RN). Never dress Android in iOS chrome.
3. **Every user-facing change goes in `src/release-notes.ts`** under the current version (same rules as the reference app's `ReleaseNotes.swift`: `new:` / `changed:` / `removed:` / `fixed:`, terse one-liners).
4. **Never `git commit` or `git push`.** The user handles git.
5. Never edit `ios/` or `android/` by hand (generated by `expo prebuild`). Configure native behavior in `app.config.ts` and config plugins.
6. Run `pnpm check` (format, lint, TypeScript 7 type check via Vite+) and `pnpm test` before declaring work done. Zero errors.
7. **No raw JavaScript in the repo.** Every source file is TypeScript (`.ts`/`.tsx`; `.mts` for Node ESM scripts in `scripts/`). Config plugins are `.ts` and imported from `app.config.ts`. `pnpm typecheck` covers both the app and the Node-side files (`tsconfig.node.json`).
8. **No EAS.** Builds are local only: `pnpm expo prebuild` + `pnpm expo run:android|ios`.
9. **iOS delivery uses Sqim, always a real-device Release build** (same rule as the Swift app). On the Mac, after every completed change:
   1. `pnpm ios:prepare` (`pnpm install --frozen-lockfile` + `expo prebuild --platform ios --clean`, installs Pods) whenever native deps or `app.config.ts` changed.
   2. From `ios/` (so Sqim picks up `Arcane.xcworkspace`, not the bare `.xcodeproj`): `sqim status`, then `DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer sqim upload --device --build`, using the **Release** configuration (check `sqim --help` for the flag). A Debug build of this app boots the Expo dev-client launcher and needs Metro, so it is useless on a phone away from the Mac.
   3. Give the user the final HTTPS install URL. Never use Sqim simulator uploads or `sqim remote-build`. Retry with `--allow-provisioning-updates` only for missing profiles; never revoke or create signing certificates without approval. If the build or upload fails, report the failure; never hand over an older link.

## Toolchain

- **pnpm only** (`packageManager` pins the version; `preinstall` rejects npm/yarn). `nodeLinker: hoisted` in `pnpm-workspace.yaml` keeps a flat `node_modules` for React Native autolinking and Metro. Shared tool versions live in the workspace `catalog`.
- **Vite+** (`vp`, configured in `vite.config.ts`) handles everything except bundling: `pnpm check` (Oxfmt + Oxlint + type check), `pnpm fmt`, `pnpm lint`, `pnpm typecheck`, `pnpm test` (Vitest; tests live in `src/**/__tests__/*.test.ts` and import from `vite-plus/test`). Metro still bundles the app.
- **No code comments.** Don't add comments, doc comments or JSX comments to any source file. The only exceptions are tool directives (`// oxlint-disable-next-line`, `// @ts-expect-error`).
- **Code style** matches the `arcane` repo: tabs, single quotes, no trailing commas, width 100. Let `pnpm fmt` do it; don't hand-format.
- **Dependencies:** Expo SDK packages (and `react`, `react-native`, gesture-handler, etc.) stay on the versions `pnpm expo install --check` reports for the current SDK; everything else stays on its latest release.

## Stack

- Expo SDK 58, React Native 0.88, React 19.3, React Compiler on. TypeScript strict + `noUncheckedIndexedAccess`.
- Routing: Expo Router (`src/app/`). Tabs use `expo-router/native-tabs` (native UITabBar → Liquid Glass on iOS 26; Material bottom bar on Android). Each tab hosts a native `Stack`.
- iOS UI: **`@expo/ui/swift-ui`** — real SwiftUI (List, Section, Form, Menu, ContextMenu, SwipeActions, Toggle, Picker, Chart, Gauge, glassEffect modifier, …). Port SwiftUI views almost line-for-line. Wrap every tree in `Host` imported from `@expo/ui` (universal root).
- Android UI: React Native views styled as Material 3 (dynamic colors from `src/theme/colors.ts`, ripple via `android_ripple`, the kit in `src/ui/material/`), plus `@expo/ui/jetpack-compose` for native controls (Switch, DropdownMenu, AlertDialog, ModalBottomSheet, SegmentedButton, Slider, progress). Icons via `src/ui/Icon.tsx` (Material Symbols mapped from SF names).
- Shared, platform-neutral `@expo/ui` universal components are fine where they cover the need.
- Icons: SF Symbols on iOS (`expo-symbols` / swift-ui `Image systemName`), Material Symbols on Android. Use `src/ui/symbols.ts` to map every SF name to a Material name.
- Glass outside SwiftUI trees: `expo-glass-effect` (`GlassView`) with `expo-blur` fallback.
- State: `zustand` stores in `src/stores/` mirroring the reference app's `@Observable` stores (same names, same logic).
- Persistence: `react-native-mmkv` via `src/core/storage.ts` — **reuse the reference app's UserDefaults key strings** (e.g. `arcane.serverURL`, `accentColorHex`). Secrets: `expo-secure-store`.
- API: `src/sdk/` is a TypeScript port of `libarcane-swift` with the same service/method names (`client.containers.list(...)`). See `src/sdk/README.md`. Swift source for reference: `~/.cache/ref/libarcane-swift`.

## Layout

```
src/
  app/                 Expo Router routes only (no .ios/.android suffixes here)
  sdk/                 Arcane API client (port of libarcane-swift)
  core/                storage, client manager glue, token store, env
  stores/              zustand stores (ports of Services/*.swift)
  theme/               colors, Radius/Motion tokens, accent color
  ui/                  shared components; platform splits as Foo.ios.tsx / Foo.android.tsx
  features/<domain>/   screens + hooks per domain (dashboard, containers, …);
                       Screen.ios.tsx (SwiftUI), Screen.android.tsx (Compose), shared hooks in .ts
  release-notes.ts
```

Shared (unsuffixed) files load on iOS too, so they must never import Android-only native modules (`@react-native-menu/menu`, `@expo/ui/jetpack-compose`). That library isn't linked on iOS, and importing it shows a red-box crash there.

Platform-split files must live **outside** `src/app/`. A route file just re-exports the feature screen.

## Shared building blocks (use these, don't re-invent)

- `src/core/storage.ts` — MMKV `defaults` + `useStoredString/useStoredBool` (`@AppStorage`), `Keys`.
- `src/core/app-tab.ts` — `AppTab` model (titles, SF symbols, colors, access rules).
- `src/theme/` — `colors` (semantic, `systemColors`, `withOpacity`, `colorGradient`), `Radius`, `Motion`, `useAccentColor()`.
- `src/ui/Icon.tsx` (RN trees), `src/ui/symbols.ts` (SF→Material map; add entries for new symbols).
- `src/ui/glass.tsx` — `GlassSurface` (Liquid Glass / material / tonal fallback) for RN trees. Inside SwiftUI trees use the `glassEffect` modifier.
- `src/ui/toast` — `showToast(Toasts.success("…"))`, activity toasts. Never use `Alert` for transient feedback.
- `src/ui/settings-row.ios.tsx`, `src/ui/material/list.tsx` — list rows.
- `src/core/networking/response-cache.ts` — in-flight GET dedup (`ResponseCache.swift`).
- `src/ui/components/` — ported shared components (see its README.md: one line per component, SwiftUI-tree vs standalone, Swift source). `.ios.tsx` files with no Android sibling (`swiftui-motion`, `swiftui-surfaces`, `*-swiftui` wrappers) may only be imported from other `.ios.tsx` files.
- Routes: every destination lives once in `src/app/(tabs)/(dashboard,…,more)/` and is shared by all tab stacks. Push with `router.push("/(tabs)/(more)/ports")`-style paths or relative `router.push("./container/abc")`.

## Porting checklist per screen

1. Read the Swift view and every helper it uses.
2. Port data loading to a hook (`useXxx`) shared by both platforms.
3. iOS: SwiftUI tree via `@expo/ui/swift-ui`, matching modifiers. Headers/toolbars via `Stack.Screen` options / `Stack.Toolbar`.
4. Android: Compose tree with the same sections, actions, and states.
5. Add a release-notes bullet only when behavior differs from the reference app or is new.

## `@expo/ui` / Hermes pitfalls (each caused a visible iOS mismatch)

- **`Host`:** in SwiftUI trees import `Host` from `@/ui/host`, not `@expo/ui`. It sets `seedColor` to the accent, matching the Swift app's root `.tint(accent)`; without it Toggles render system green and other tinted controls system blue.
- **`systemColors`** resolve on each read for the current light/dark appearance and iOS version (iOS 26 retuned the palette). Read them during render; don't copy them into module-level constants, which freeze one appearance.
- **SF Symbols:** import `Image` from `@/ui/components/swiftui-image`, never from `@expo/ui/swift-ui`. Expo's `Image` forces `font(size: 24)` when it has no font modifier, so symbols ignore the parent font that SwiftUI would inherit.
- **`strokeBorder` on a shape** (`RoundedRectangle`, `Circle`, …) overlays the stroke on a shape that still fills with the foreground color, which hides everything under it. Put `foregroundStyle("#00000000")` first and pass `shape` / `cornerRadius` (it defaults to an 8pt rectangle).
- **`ContentUnavailableView` + buttons** (Swift's `actions:`): use `UnavailableView` from `@/ui/components/unavailable-view` (`actions` or `children`). It reproduces Swift's action spacing and subheadline buttons to within 1pt. Don't hand-roll a `VStack` of `ContentUnavailableView` plus `Button`: the view fills the screen and pushes the buttons to the bottom.
- **Header toolbars:** use `AppToolbar` from `@/ui/app-toolbar` (port of `AppToolbarItem`, accent-tinted symbols). `Stack.Toolbar`'s `tintColor` doesn't reach items. Swift's `ToolbarSpacer(.fixed)` between items = `separateBackground` on the following item.
- **SwiftUI `Toolbar.Content`** (sheets with their own `NavigationStack`) draws `ToolbarItem`s that share a placement in reverse declaration order. Declare them reversed relative to Swift, with a comment. `AppToolbar` header items are unaffected.
- **Tappable rows:** a `buttonStyle("plain")` Button only registers taps on its opaque content, so the `Spacer` gap in a row ignores taps. Give the row's HStack `contentShape(shapes.rectangle())` so the whole width is tappable, like a Swift `NavigationLink` row.
- **`foregroundStyle("tertiary")` / `"quaternary"`** are silently dropped, so the text renders at full brightness. Use `foregroundStyle({ type: "hierarchical", style: "tertiary" })`. Use the hierarchical form for `"secondary"` too: the plain string gives `Color.secondary` (bluish `#98989F`), while Swift's `.foregroundStyle(.secondary)` is hierarchical (neutral `#8E8E8F`, and it picks up the tint inside tinted buttons). Keep the plain color only where Swift explicitly uses `Color.secondary`. `"primary"` has the same problem inside Button labels: Swift's `.primary` there takes the button's tint, so use `{ type: "hierarchical", style: "primary" }` in those spots. Elsewhere the two are equivalent.
- **State-driven `<Alert isPresented>`** with no `Alert.Trigger` renders an `EmptyView`, so the alert never appears. Put `<AlertAnchor />` (from `@/ui/components/alert-anchor`) as its first child, and place the alert (or `ActionErrorAlert`) beside the `List`/`Form` inside the `Host`, never inside it. Inside a List, the anchor renders as an empty row.
- **Nested `<Text>` runs** don't re-render reliably; build changing strings as one `Text` (or a `ZStack` of `Text`s).
- **RN views inside SwiftUI** (`RNHostView`) need a fixed SwiftUI `frame` around a `matchContents` host, or they drift out of their slot.
- **Hermes has no `Intl.RelativeTimeFormat`**: use `relativeTimeFormat()` from `@/core/relative-time`.
- **Decode API payloads** that have a Swift `init(from:)` (e.g. `DockerInfo.decode`) when fetching through `boundedDirectResponse`; raw JSON silently yields zeros.
- **Launch screen:** iOS caches it per bundle ID across reinstalls; restart the device/simulator to see a change.
